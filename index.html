견적 기반 발주 설계·구축

  • 개시 7개월 차 월 거래액 5천만원, 전고점 갱신
  • 배송 계약 종료로 거래액이 절반이 된 발주 서비스를 견적 기반 발주로 재설계
기간
  • 1차 구축2025.10 – 2025.12 (개시 2025.12)
  • 확장2026.02 – 03 (토스페이먼츠 결제·서비스 이용료)
  • 리뉴얼2026.06 – 07 (견적 문의 묶음·라우팅, 직납·간납 결제 분리, 배포 2026.07)
역할
  • 프로덕션팀 팀장 겸 백엔드 엔지니어
  • 정책·도메인 설계, 백엔드 단독 구현, 내부 어드민 프론트엔드

결과

  • 월 거래액 5천만원(2026.07, 개시 7개월 차)으로 전고점 약 4,500만원(2024.07)을 넘었습니다.
  • 월 신규 가입 상점의 발주 전환율은 최고 15%였습니다.
  • 이 수치는 1차 구축, 확장, 리뉴얼과 가입 상점 대상 영업 활동이 함께 만든 결과입니다.

배경

기존 발주 서비스는 배송 계약이 끝나며 경쟁력을 잃었고, 월 거래액이 전고점 대비 50% 줄어 2천만원 초반까지 내려갔습니다.

지역 파트너 도매사를 연계하려 했지만 도매사는 상점마다 단가가 달라, 정찰가 발주 대신 견적 흐름으로 주문 도메인을 다시 설계했습니다.

견적가는 홈택스로 수집한 상점의 실제 매입가, 도매사 매입가, 플랫폼 내부 거래 데이터를 종합한 지표로 산출했습니다.

국세청 거래내역의 매입·매출 데이터로 국내 주류 시장 흐름을 파악할 수 있어, 상점에게 최적화된 견적을 줄 수 있었습니다(국세청 거래내역 수집·매칭).

핵심 설계 판단

정찰가 발주를 확장하지 않고 견적 도메인을 분리, 판매자 유형별로는 진입 경로만 나눔

  • 문제 정찰가 발주는 담는 순간 가격이 정해지지만, 견적 발주는 요청 → 견적 제시 → 상점 확인을 거쳐야 정해져 상태 흐름이 근본적으로 달랐습니다.
  • 선택 기존 발주 모델에 견적 상태를 더해 하나로 합치는 대신 견적 도메인을 따로 설계했습니다. 합치면 두 흐름의 분기가 모델 곳곳에 들어가 양쪽 모두 복잡해진다고 판단했습니다. 판매자 유형에 따라 달라지는 것은 가격 확정 방식뿐이라고 보고 진입 경로만 나눴습니다. 도매사 상품은 견적을 거치고 공급사 상품은 바로 발주하며, 발주 확정 이후 흐름은 공유했습니다. 판매자마다 두 경로 사이를 유연하게 전환할 수 있어야 했기 때문입니다.
  • 결과 기존 서비스를 멈추지 않고 2025.12에 개시했습니다. 기존 공급사를 그대로 수용하면서 도매사 상품을 추가했고, 출고 확정·정산·세금계산서 발행은 한 곳에서 관리했습니다.

서비스 이용료율을 코드 상수에서 정책 테이블로

  • 문제 결제수단별 요율이 코드 상수라 모든 판매처에 같은 요율이 적용됐는데, 판매처·기간마다 다른 요율이 필요해졌습니다.
  • 선택 예외만 행으로 두는 단일 테이블 대신, 판매처·기간 정책과 기본 정책 대체를 갖춘 구조로 기본 요율까지 DB로 옮겼습니다. 발주 품목 완료 시점의 요율 행을 참조로 저장해, 금액을 중복 저장하지 않고도 금액 고정과 정책 추적이 되게 했습니다.
  • 결과 요율은 배포 없이 데이터 변경만으로 바꿀 수 있게 됐고, 이후 결제 게이트웨이를 바꿀 때도 공급사 정산은 이 정책 기준으로 계속 동작했습니다.

결제 전환: 직납 카드 결제를 KG에서 토스로, 되돌릴 수 있게

  • 문제 지급 대행 조건이 더 좋은 토스페이먼츠로 결제를 옮기면서, 다른 담당자가 만든 KG 기반 직납 카드 결제를 바꿔야 했습니다.
  • 선택 회의를 직접 주재해 기존 KG 흐름을 처음부터 다시 짚었고, "결제됨" 판정이 KG만 보던 지점을 찾아 두 게이트웨이를 모두 인식하게 바꿨습니다. 전환 후 KG 분할정산이 주류 거래의 법적 구조에 더 맞다는 판단이 나와, KG 경로를 지우지 않고 설정값 하나로 오가는 구조를 더했습니다.
  • 결과 모델 변경 없이 직납 카드 결제를 오류 없이 토스로 전환해 운영했고, KG 복귀는 일정만 잡은 채 실행 전에 퇴직했습니다.

국세청 거래내역 수집·매칭

  • 세금계산서 품목 약 2천만 건을 수집·매칭하는 파이프라인 단독 구축
  • 매입·매출 데이터로 국내 주류 시장 흐름을 파악해 견적 기반 발주의 견적가에 활용, 닐슨IQ 데이터 제공 계약으로도 이어짐
기간
  • 2022.05 – 2026.08 (첫 수집 2022.06, 퇴사 시점까지 운영·개선)
역할
  • 기획 리서치·구조 설계부터 수집, 매칭, 검색 인덱스, 확정 어드민 화면까지 단독 구현
  • 초기 매칭 확정 작업 직접 수행
  • 닐슨IQ 데이터 제공에서는 데이터 추출·가공, 데이터 모델링, 전달 방식·포맷 지정, 기술 미팅 참여

결과

  • 세금계산서 품목 약 2천만 건을 2022.06 첫 수집부터 2026.08 퇴사 시점까지 확보했습니다.
  • 주류 품목 줄 기준 매칭률 80% 수준을 2024년 이후 계속 유지했습니다.
  • 수집 데이터는 닐슨IQ와 연 억 단위 데이터 제공 계약으로 이어졌고, 2023년부터 퇴사 때까지 매월 전달했습니다 (닐슨IQ 파트너십 기사, 2023.07).

배경

플랫폼 내부 발주 데이터만으로는 상점이 실제로 어떤 상품을 어떤 단가에 매입하는지 알 수 없었습니다.

주류는 세금계산서 의무 발행 대상이라, 국세청 거래내역을 확보하면 사업자의 주류 매입·매출 내역을 빠짐없이 볼 수 있습니다.

핵심 설계 판단

홈택스 직접 연동 대신 하이픈 경유

  • 문제 홈택스는 공개 API로 세금계산서를 내주지 않고, 인증 방식과 화면 구성도 정부 정책에 따라 바뀝니다.
  • 선택 직접 연동 대신 스크래핑 전문 업체 하이픈 경유를 택했습니다. 직접 연동은 외부 비용이 없지만, 변경이 생길 때마다 우리가 대응해야 해 유지 비용이 계속 발생하기 때문입니다.
  • 결과 하이픈 응답 형식 변경(2024.11)과 홈택스 아이디 인증 방식 변경(2025.07) 때 우리 쪽 대응은 인증 입력값과 응답 처리 범위 안에서 끝났습니다.

가매칭은 기존 Elasticsearch 검색을 재사용하고, 확정은 이력 재사용으로 자동화

  • 문제 세금계산서 품목명은 공급자가 자유롭게 적는 텍스트라 같은 상품도 표기가 제각각이고, 가매칭 결과를 매번 사람이 확인하면 수집량만큼 확인 작업도 늘어납니다.
  • 선택 전용 매칭 엔진 대신 형태소 분석과 동의어 사전을 적용해 둔 주류 검색 인프라로 가매칭했습니다. 한 번 확정한 GTIN이나 같은 판매자의 같은 품목명은 이후 자동 확정했고, 같은 문자열도 판매자마다 다른 상품일 수 있어 품목명 재사용은 같은 판매자 안으로 한정했습니다.
  • 결과 확정 이력이 쌓일수록 수동 확인 대상이 줄었고, 퇴사 시점에는 매칭된 품목 대부분이 사람 확인 없이 자동 확정됐습니다.

집계 테이블만 두지 않고 세금계산서 전용 검색 인덱스로 조회

  • 문제 거래 데이터가 쌓이면서 상점별·상품별 집계와 조건 검색 요구가 늘었고, RDB 조회로는 응답 속도와 추출 유연성 모두 대응이 어려웠습니다.
  • 선택 집계 테이블은 정해진 기준의 집계만 빠르게 낼 수 있어, 자유 검색어 지원을 위해 2024.11 세금계산서 매칭 내역 전용 인덱스를 만들고 매칭 행이 생기거나 바뀔 때 동기화했습니다.
  • 결과 견적가 산출용 최근 실거래 단가 통계, 도매사 매입 요약, 공급사 거래 데이터 조회가 같은 인덱스 위에 올라갔습니다.

통합 주류 발주 플랫폼 파도

  • 출시 4개월 만에 월 거래액 4천만원 (서비스 전체)
  • 주문 의사만 전달하던 발주를 결제·배송·정산까지 처리하는 커머스 구조로 설계
기간
  • 1차 구축2023.09 – 2024.02
  • 확장2024
역할
  • 백엔드 엔지니어 (1차 구축 팀: 백엔드 2명(본인 포함), 프론트엔드 1명, 디자인 1명)
  • 서비스 전반의 Django 도메인 모델링, 발주·정산 영역 담당
  • 1차 구축 때 WMS 배송·KG 결제·구독은 별도 담당자와 협업, 이후 확장·유지보수는 본인

결과

  • 서비스 전체 기준으로 공급사 20곳이 온보딩했습니다.
  • 서비스 전체 기준으로 출시 4개월 만에 월 거래액 4천만원(2024.06)을 기록했고, 전고점은 약 4,500만원(2024.07)입니다.
  • 본인이 맡은 세금계산서 위수탁 발행(확장)은 2곳을 제외한 모든 공급사가 이용했습니다.

배경

기존 벨루가 주류 발주는 주문 의사만 전달했고, 결제와 배송은 시스템 밖에서 처리됐습니다.

파도는 한 발주에 여러 공급사의 상품이 섞이는 구조라, 공급사마다 이용료·정산·세금계산서를 따로 처리해야 했습니다.

핵심 설계 판단

발주와 발주 품목 분리, 상태는 품목 단위 (1차 구축)

  • 문제 발주 하나에 상태 하나를 두면 공급사별 부분 취소·부분 배송을 표현할 수 없었습니다.
  • 선택 단일 상태나 공급사별 발주 분리 대신, 발주와 발주 품목을 나누고 출고·취소 상태를 품목에 두었습니다. 배송이 HL 홀딩스 WMS로 통합되어 있어, 공급사별 분할 정산만 되면 상점이 한 번에 발주하는 것이 맞다고 판단했습니다.
  • 결과 확장 기간에 판매자 직접 배송이 추가됐을 때, 새 흐름을 품목 상태 위에 그대로 얹을 수 있었습니다.

세금계산서와 발주를 M2M으로, 발행 상태는 한 곳에 (확장 2024)

  • 문제 세금계산서는 여러 발주를 묶어 통합 발행하기도 하고, 한 발주에 공급사별 세금계산서가 여러 장 연결되기도 합니다.
  • 선택 발주에 세금계산서를 매달거나 발행 상태 필드를 두는 대신, 세금계산서와 발주를 M2M으로 연결했습니다. 발행 여부는 연결된 세금계산서로 판단해, 두 곳의 상태가 어긋나지 않게 했습니다.
  • 결과 발행 상태가 한 곳에만 있어 상태 중복에 따른 불일치가 생기지 않습니다.

세금계산서는 출고 확정 후 3일 뒤 발행 (확장 2024)

  • 문제 발행 뒤 발주가 취소·변경되면 수정세금계산서를 발행해야 하고, 그 부담이 공급사에게 넘어갑니다.
  • 선택 발주 확정 직후 발행 대신, 취소 가능 구간을 지나도록 출고 확정 후 3일 뒤 Celery 워커가 발행하게 했습니다. 발행 요청 전까지는 공급사가 발행을 중단할 수 있습니다.
  • 결과 수정세금계산서 발행 건 자체를 줄였고, 이후 견적 발주에도 같은 발행 구조를 적용했습니다.

핵심 설계 판단

MySQL 전문검색 대신 Elasticsearch 도입

  • 문제 표기 변형을 처리하려면 형태소 분석과 동의어 처리가 필요했고, 검색 쿼리가 주 DB에 부하를 주고 있었습니다.
  • 선택 MySQL 전문검색(FULLTEXT) 대신 Elasticsearch를 택했습니다. FULLTEXT는 형태소 분석기와 동의어 사전을 지원하지 않아 애플리케이션에서 검색어를 치환해야 했고, Elasticsearch는 Nori와 동의어 사전을 표준 기능으로 지원하기 때문입니다.
  • 결과 검색 부하가 RDB에서 분리됐고, 표기 변형 처리를 코드가 아니라 검색 엔진 설정(analyzer)으로 관리하게 됐습니다.

주류 데이터로 사전을 직접 구축하고 analyzer를 목적별로 분리

  • 문제 주류 상품명은 대부분 고유명사라 Nori와 범용 사전만으로는 의미 단위 분리와 표기 변형 대응이 되지 않았습니다.
  • 선택 범용 사전 대신 내부 주류 데이터에서 사용자 사전과 동의어 사전(국가, 포도 품종)을 직접 만들었습니다. shingle 처리와 동의어 처리는 한 analyzer에서 함께 쓸 수 없어, 같은 상품명 필드를 analyzer별로 나눠 색인했습니다.
  • 결과 사전은 이후 계속 늘어, 2026년 저장소 기준 주류 사용자 사전 9,649줄, 포도 품종 동의어 555줄입니다.

시점별 인덱스와 alias 교체로 무중단 전환, 복구는 재색인

  • 문제 매핑과 사전은 계속 바뀔 예정이었고, 재색인하는 동안 검색이 멈추면 안 됐습니다.
  • 선택 1차 구축 중 같은 인덱스에 덮어쓰는 방식에서 alias 교체 방식으로 전환했습니다. 생성 시각을 붙인 새 인덱스에 색인한 뒤 alias를 한 번의 요청으로 옮기고, 이전 인덱스는 삭제해 문제가 생기면 MySQL에서 재색인해 복구합니다.
  • 결과 이후 매핑·사전 변경과, 동료와 함께 진행한 2024년 OpenSearch 이전의 인덱스 재생성을 모두 같은 절차로 처리했습니다.

도매사 폐쇄몰 발주닷컴

기간
  • 2022.12 – 2023.02
역할
  • 백엔드 단독 담당(기획·프론트엔드는 다른 담당자)

결과

  • 퇴사 시점 기준 도매사 2곳이 폐쇄몰을 실제로 사용했습니다.

배경

도매사들은 상점 발주를 수동으로 받고 있었고, 이 업무를 최적화하려고 도매사 전용 폐쇄몰을 만들었습니다.

도매사는 자기 거래처 상점에게만 상품을 보여주고 발주를 받으며, 어드민에서 상품·거래처·발주를 관리합니다.

핵심 설계 판단

도매사 구분을 접속 도메인(Origin)으로 판별하는 인증 구조

  • 문제 도매사마다 자기 거래처 전용 폐쇄몰이 필요했지만, 도매사별로 서버를 따로 두면 도매사가 늘 때마다 인프라도 늘어납니다. 이용자가 도매사의 거래처 상점이라, 도매사별로 월 접속이 예상되는 상점이 최대 100곳 수준으로 적었습니다.
  • 선택 하나의 백엔드가 요청의 Origin 헤더에서 서브도메인 접두어를 읽어 어느 도매사 폐쇄몰인지 판별하게 했습니다. 폐쇄몰 로그인 토큰은 벨루가 토큰과 다른 키로 구분하고, 해당 도매사에 접근 권한이 없는 계정은 403으로 막았습니다. 지정된 Origin에서만 이 인증을 거치게 해 기존 벨루가 서비스에는 영향이 없게 했습니다.
  • 결과 새 도매사는 인프라 확장 없이 도메인(Route53) 설정과 도매사 접두어 등록만으로 추가할 수 있고, 여러 도매사가 같은 서버를 병렬로 쓸 수 있도록 설계했습니다.

주요 구현

  • 상점 기능: 도매사별 상품 검색, 장바구니, 발주와 발주 취소를 구현했습니다.
  • 발주 시점 값 보존: 발주에는 상점·도매사 정보를, 발주 품목에는 상품·주류 정보를 복사해, 이후 정보가 바뀌어도 지난 발주 내역이 그대로 남게 했습니다.
  • 마감·배송일 계산 통일: 도매사 영업시간, 배송 요일, 공휴일을 반영해 발주 마감 시각과 배송일을 한 로직으로 계산하고, 발주 품목은 마감 시각 전까지만 취소할 수 있게 했습니다.
